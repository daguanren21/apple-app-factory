# Platform UI: native adaptation and real-surface evidence

Use with the [UI design guide](ui-design-guide.md) and [host-native skill discovery](skill-discovery.md). This guide owns platform correctness; the actual Figma reference, repository design intent and executable component/token system own visual intent. Optional specialist skills are selected through the host for the actual task, not copied or fixed by apphx. This is not permission to change framework, install a library or alter the frozen verification contract.

## Scope and invariants

apphx supports `flutter`, `android-java`, `swift`, `react-native`, `expo`, `uni-app` and `mygo`. Java Android targets Android; Swift targets iOS; MyGo targets macOS/local delivery. The cross-platform mobile stacks must be reviewed on each platform/device class actually in the task. Desktop guidance here does not grant macOS support to another apphx stack. Browser responsive previews do not stand in for native apps.

Before editing, identify the real host, framework/version, min OS, navigation/chrome owner, target device classes, allowed orientations, existing inset handling, keyboard policy, text scaling and motion preference APIs. Reuse their owning components; fix an inset at its owner rather than adding offsets to every screen.

- **One owner per edge.** Native bars, navigation containers, scroll views and page content must not each add the same inset. Record which layer owns top, bottom, left/right and keyboard avoidance. Backgrounds may intentionally extend under system chrome; readable content, focused fields and controls must remain inside the usable region. Recheck contrast of status/navigation-bar icons over the real background.
- **Use live geometry, not device names.** No hard-coded status-bar/notch/home-indicator padding or screen-size constants used as insets. Respond to actual window bounds, display cutouts, orientation, split-screen and keyboard changes. Keep native back/edge gestures usable.
- **Adapt structure, not just scale.** Reflow navigation, panels and action placement at content-driven constraints. Narrow windows retain the same essential tasks; wide windows use space intentionally, not a stretched phone column. Long content scrolls; fixed controls reserve space instead of covering the last item.
- **Text is layout input.** Follow system scaling and semantic text styles, support wrapping/localization, and keep critical labels/actions visible at large text. Do not disable scaling, shrink all text, crop labels or lock orientation to hide overflow. Truncation of noncritical content needs an accessible way to read it fully.
- **Input and focus are first-class.** Keep focused controls visible when the IME opens; preserve input, selection and scroll position on keyboard dismissal and resize. Verify hardware keyboard order, visible focus, shortcuts, dialog dismissal/focus return and touch/pointer alternatives where supported. Never use hover as the only affordance.

## Stack implementation routes

### Flutter — iOS and Android

- Let `Scaffold`, app bars/navigation bars and `SafeArea` own the appropriate edges. A custom full-bleed background can sit outside `SafeArea`; place interactive content inside it. Avoid wrapping a bar that already handles its edge in another unconditional inset.
- Use `MediaQuery.viewPadding` for stable system padding and `MediaQuery.viewInsets` for fully obscured regions such as the keyboard; they are different measurements. `SafeArea` consumes padding for descendants. Derive any remaining custom padding from the actual widget context, not a global cached screen measurement.
- `Scaffold.resizeToAvoidBottomInset` normally resizes the body for the keyboard. Do not also add the entire `viewInsets.bottom` to that already-resized body. If a custom overlay/bottom sheet owns keyboard avoidance, explicitly choose its resize/inset owner, use the current inset and a scrollable form, and reveal the focused field. `maintainBottomViewPadding` is a targeted stability choice, not a blanket keyboard fix.
- Use `LayoutBuilder` for available constraints and responsive composition; `MediaQuery.sizeOf` describes the view, not necessarily a nested pane. Account for `displayFeatures` when the shipped device class includes a hinge/cutout. Do not reduce all targets to portrait phone width.
- Respect `TextScaler` and the theme's semantic text roles; avoid a global fixed/no-scaling override. Use wrapping/flexible children and scrollable content rather than unbounded fixed-height rows. Respect `MediaQuery.disableAnimations` and the project's accessibility conventions; settle controllers to the correct state when motion is disabled, canceled or the route is disposed.
- **Capture:** run the actual Flutter app in the selected iOS simulator/Android emulator or device. Capture a small usable area and a wider/taller supported configuration, an active keyboard over the lowest field/action, large text, and normal/reduced-motion interaction. A web build or widget golden alone does not show native bars, IME or navigation behavior.

### Java Android — native Views

- Use the existing Activity/window's supported edge-to-edge policy and `WindowInsets`/`WindowInsetsCompat` APIs for `systemBars`, `displayCutout` and `ime`. Honor the target SDK's edge-to-edge behavior; do not treat changing status-bar color as restoring legacy content bounds.
- With AndroidX already present, `ViewCompat.setOnApplyWindowInsetsListener` can apply required edges to the owning container. Preserve its baseline padding/margins and add current insets to that baseline, not to the last applied value. Do not consume insets before a child that needs them receives them. Without AndroidX, use the project's supported platform API; this guide does not require a dependency installation.
- A root that resizes for IME must not receive the same keyboard height again as padding. Coordinate `adjustResize`, the app's inset policy and any `WindowInsetsAnimation`/compat handling. Put forms in a viewport-aware scrolling container and keep focused fields plus submit/recovery actions reachable; test keyboard show, hide and back dismissal.
- Size layout in `dp`, text in `sp`; use system font scaling and content-aware layout. Choose panes/navigation from available window size, not physical display size. Test multi-window and supported landscape, and hinge/posture only when that device class ships.
- Use native/material navigation appropriate to the existing app; preserve system/predictive back where supported. Standard Android target size is at least 48×48dp. Respect the system animation setting through the APIs available at the pinned API/dependency level (for example `ValueAnimator.areAnimatorsEnabled()` where supported); do not make business state depend on an animator completion listener.
- **Capture:** launch the installed app on the specific authorized emulator/device, with system bars visible. Exercise edge-to-edge/cutout and gesture navigation; include three-button navigation when supported, IME-open content, large font/display scaling, constrained/wide windows and disabled/reduced animation. Source inspection or a layout preview cannot establish these outcomes.

### Swift — iOS, UIKit or SwiftUI

- **UIKit:** constrain actionable content to the correct view's `safeAreaLayoutGuide`; let navigation/tab controllers and scroll-view adjusted content insets do their existing jobs. Recalculate custom layout on safe-area/window changes instead of caching status-bar height. On supported deployment targets use `keyboardLayoutGuide` for keyboard-relative controls; older-target handling must use the established project mechanism, convert keyboard frames into the view's coordinates and avoid double-counting safe area. Floating/split keyboards are not always a full-width bottom rectangle.
- **SwiftUI:** the normal layout respects safe areas. Use `safeAreaInset` for custom bottom/top actions where appropriate; limit `ignoresSafeArea` to intended background or media layers, not an entire interactive root or keyboard region. Use scrollable forms, `FocusState` and the project's navigation containers. Do not disable automatic keyboard avoidance as a way to stop a layout jump.
- Derive compact/expanded structure from available size and size classes, including iPad multitasking where targeted. Preserve system back gestures, sheet dismissal semantics, native navigation and accessible controls. Standard iOS touch targets are at least 44×44pt.
- Use Dynamic Type text styles, `UIFontMetrics`/`adjustsFontForContentSizeCategory` for custom UIKit fonts and `@ScaledMetric` where supporting SwiftUI dimensions need scaling. Test an accessibility text size; do not globally cap `dynamicTypeSize` to make a screenshot fit.
- Observe `UIAccessibility.isReduceMotionEnabled`/its change notification or SwiftUI `accessibilityReduceMotion`. Replace nonessential spatial motion with immediate state or a restrained fade; retain focus and meaningful feedback.
- **Capture:** use the actual running simulator or device and name its UDID/model/OS, not a browser recreation. Capture iPhone cutout/home-indicator states and iPad/split-view if targeted, keyboard open, large Dynamic Type, supported orientations, appearances and Reduce Motion. Simulator evidence does not establish physical-device gesture feel or frame rate.

### React Native — native iOS and Android

- Use the project's `react-native-safe-area-context` provider/hooks/components when present, or its existing supported native inset abstraction. The provider must cover the relevant native route/modal root. Apply only edges not already handled by the navigation header/tab bar; do not nest unconditional top/bottom padding or reuse an initial inset forever. Do not add a new library without the task's approval.
- Coordinate `KeyboardAvoidingView`, the navigation header's measured offset, a scrolling form and Android's window resize/inset behavior. Choose behavior per platform and actual layout; no universal constant `keyboardVerticalOffset`. Check the bottommost input, footer action, modal and keyboard-dismiss path, not just the first field.
- Prefer `useWindowDimensions`/current container layout to cached `Dimensions.get` values. Reflow panels at actual available width; a device can resize without changing identity. Keep `allowFontScaling` enabled and handle long/wrapped text instead of imposing a blanket `maxFontSizeMultiplier` cap.
- Preserve native accessibility roles/labels, focus behavior and platform navigation. Use `AccessibilityInfo.isReduceMotionEnabled()` and the established preference-change subscription where custom motion needs it; cancel/remove listeners according to the installed version. Existing Animated/Reanimated or native transitions may be used, but are not a reason to install another runtime. Keep state correctness independent from transition callbacks.
- **Capture:** run the actual native host on each shipped platform with small/wide layout, bars/gestures, keyboard, large fonts and reduced motion. Storybook, a JS unit test or React Native Web in a browser is supplementary, not native acceptance.

### Expo — preserve its actual native workflow

Apply the React Native route, then inspect the pinned Expo SDK, router/navigation containers and installed modules. Keep the existing managed or prebuilt structure; no forced `prebuild`, ejection, SDK upgrade or cloud build for this guide.

- Account for Expo Router/navigation-owned safe areas and headers; do not add another universal wrapper around them. Use the installed safe-area implementation at the correct route/modal boundary.
- Treat status/navigation-bar configuration and Android edge-to-edge behavior as native host behavior. Match the SDK's actual API support rather than assuming a bar-color or translucency setting can restore old bounds.
- Keep keyboard layout, window sizing, text scaling and accessibility motion preference handling consistent with the React Native route. Verify production-relevant navigation/modal behavior in the owner's actual development build or app. Expo Go may provide useful observations but is not proof for native capabilities/configuration absent from that host.
- **Capture:** record the runtime used (Expo Go/development build/packaged app), SDK/platform and limitations. Final native acceptance must exercise the real target configuration, not only the web export.

### uni-app — App/WebView and native-rendered pages

Preserve the actual CLI or HBuilderX project, `manifest.json`/`pages.json`, renderer and owner-maintained native host. H5 and native App are not interchangeable test targets.

- Determine whether the native title bar/tab bar or the page owns each edge. For custom navigation, use the target/version's supported `uni.getWindowInfo()` safe-area/window measurements or the project's established inset API; no guessed status-bar heights. React to supported window/orientation events and respect keyboard resize configuration.
- On actual WebView/H5-rendered pages, use `env(safe-area-inset-top/right/bottom/left)` where the host exposes those values and `viewport-fit=cover` where applicable. An inset already consumed by the native host must not be added again in CSS. A fixed footer needs usable bottom clearance and reserved scroll space, not merely visual padding.
- Use current visible height, `dvh` where supported, and the actual keyboard/visual-viewport behavior. `100vh` or `100dvh` alone is not proof of keyboard safety; native wrappers and WebViews differ. Subscribe to the existing supported keyboard-height/window mechanism only when necessary, clean it up, and avoid simultaneous host-resize plus full keyboard-padding compensation.
- `rpx` adapts to width, not automatically to accessibility text size. Verify actual OS font scaling in the shipped renderer, use its supported text-scaling behavior, wrapping and accessible controls. Native-rendered/nvue pages need native layout/inset APIs, not DOM/CSS assumptions.
- For WebView CSS use `prefers-reduced-motion`; where the native renderer does not expose it, use the project's supported platform preference integration. Do not fabricate a preference bridge or report reduced motion tested if it cannot be observed.
- **Capture:** run the packaged/native App target with its real header/tab bar, active keyboard, lowest action, cutout/home gesture area, large text and reduced motion at two supported sizes. H5 browser screenshots can supplement web-content findings but cannot satisfy native App acceptance.

### MyGo — macOS native UI or WKWebView frontend

Preserve exactly the project's supported mode: Go-only native UI (`go.mod` and `mygo.json`) or the existing web frontend (`go.mod`, `mygo.config.ts`, actual frontend package manager/lockfile). Do not convert one to the other. Keep the pinned MyGo API; use public window/layout facilities and the existing bridge, not invented APIs or importable internal packages.

- Work from the **content area**, not the outer frame or full monitor size. Read current window/content geometry (`ContentSize` in projects using that supported API), and respect the host's title bar/toolbar, traffic-light buttons and native content layout. Default native chrome is preferable to unnecessary custom chrome. If full-size content or a custom title area is required, the actual native layout must reserve system-control space; CSS mobile safe-area variables alone do not describe macOS traffic lights.
- Define the smallest supported usable window with the project's existing window API; ensure every primary action still works at that size, then exercise live resizing to a normal and wide window. Use adaptive panes, wrapping, scrolling and appropriate dialog/sheet sizing. A minimum-size constraint is not a substitute for repairing clipping at the promised minimum.
- Treat Retina/backing pixels separately from logical points. Avoid using image-pixel dimensions as layout points. Verify large text or the product's supported text/zoom setting, OS accessibility settings that actually affect this renderer, and display scaling. A custom native renderer does not automatically inherit AppKit text scaling; prove its behavior. For WKWebView content use relative text sizing and the application's existing zoom/accessibility behavior without clipping the native frame.
- Test pointer hit areas, visible keyboard focus, Tab/Shift-Tab, text selection/editing, default/cancel actions, Escape and the product's real Cmd shortcuts. Menus, popovers, dialogs and sheets must stay on-screen and restore focus. Include IME composition in editable text; mobile keyboard-avoidance padding does not belong on desktop merely because an input gained focus.
- Honor macOS Reduce Motion through the pinned renderer/host's existing supported preference integration. WKWebView content may use `prefers-reduced-motion`; native/custom rendering must observe the actual macOS preference via its supported bridge. If the required platform capability is not exposed, report that prerequisite to the integration owner instead of importing internals or claiming a CSS flag controls native transitions.
- **Capture:** launch the actual visible macOS app and drive real controls. Capture the complete window including title bar/traffic lights for chrome checks, plus content images at the minimum and wide sizes. A page-only capture (`CapturePage` where available) may document content but cannot by itself prove native chrome clearance. Include keyboard focus/dialog state, scaled text and normal/reduced motion. A localhost browser, hidden/minimized window, headless view or Go test is not a desktop runtime review.

## Motion contract

For each material transition name its trigger, purpose (feedback/state/continuity/explanation), frequency, from/to state, spatial relationship, existing semantic token or native transition, interruption/reversal behavior, focus ownership and reduced-motion equivalent. Discover an appropriate specialist skill only when its expertise helps this task; no named provider or effects library is mandatory.

- Prefer immediate feedback for high-frequency actions; a small coherent transition beats repeated entrance choreography. Keep content and controls available without waiting for animation.
- Retarget/cancel obsolete motion on rapid intent changes. Open→close→open, navigation away, cancellation and reduced motion must all reach the correct state. Business state must not depend solely on `animationend`, an animator completion listener or a delayed timer.
- Reuse platform-native or existing project motion. Prefer inexpensive properties for frequent motion, bound simultaneous effects and pause nonessential loops when hidden. Do not install a library for a transition the current stack already supports.
- Reduced motion preserves information with instant updates or restrained color/opacity feedback; remove large translation, parallax, scaling and unnecessary continuous motion. Focus and accessibility announcements must still follow the real state.
- Observe normal speed, reversal/interruption, keyboard/focus and the reduced-motion mode on the running target. Save a recording or genuine runtime trace that identifies those actions/settings. A pair of still images cannot prove motion. Report measured frame timing only when a real trace/device measurement supports it; never infer “60fps” from code or a smooth simulator recording.

## Capture and acceptance matrix

The following is the minimum **evidence plan**, not a claim that this guide performed it. Apply all materially affected states and all supported device classes in scope; do not invent a new tablet, orientation or platform requirement that the app does not ship.

| Check | Mobile surface | Desktop surface | Required observable evidence |
|---|---|---|---|
| `system-insets` | Top status/cutout and bottom home/gesture areas, native navigation, active overlays; controls remain visible/tappable | Native title bar, traffic lights, toolbar/content boundary, dialogs | Actual PNG/JPEG showing the relevant system/native region, not a crop that hides the defect |
| `responsive-layout` | Small/narrow usable area and distinct wider/taller supported geometry; permitted rotation/split-screen as applicable | Minimum usable and wide window, with a resize path and scrolling | At least two distinct image geometries with viewport/device/state recorded; preserve primary tasks and no accidental clipping/overlap |
| `keyboard-focus` | Lowest field/action with IME open, keyboard dismissal and focus traversal when supported | Visible keyboard focus, Tab/Shift-Tab, shortcuts, dialog open/dismiss/focus return; IME composition for editable text | Images, video or real trace of the actual interaction; mere source labels are insufficient |
| `text-scaling` | Large OS font/Dynamic Type, long/localized content, important actions reachable | Supported large text/zoom and high-DPI/display-scale behavior | Image or real trace recording the setting/scale and visible result, not a claim that relative units were used |
| `motion` | Real transition, rapid interruption/reversal and reduced-motion equivalent | Same in the actual application window, including focus preservation | Video or genuine runtime trace identifying normal/reduced settings and actions; screenshots alone cannot pass |
| `visual-design` | Actual primary screen and relevant loading/empty/error/success states compared with Figma or existing approved design | Same with intentional desktop composition | Actual image plus observations about hierarchy, typography, spacing, contrast, component consistency and source of visual authority |

Record device/emulator/simulator identity, OS, app/route/state, image pixel dimensions, logical viewport/content size when different, text/display scale, appearance, keyboard and motion settings. For a full-window macOS image identify both frame and content bounds. Include visible bars/chrome where their clearance is claimed. Do not edit screenshots to move controls, remove overlaps, invent devices or hide failures. Fixture data must not expose personal information.

Use the task's existing authorized capture tools and **configured** `spec.screenshotsDir` under the project directory (normally generated `build/screenshots`). For MyGo, keep it outside `build/darwin-arm64`, which packaging replaces. Paths in `uiQuality.captures` are project-relative, portable paths inside that directory, never absolute/traversal/symlink paths. Each capture records its real byte SHA-256, `kind`, actual pixel `viewport.width`/`height`, `device` and `state`; image dimensions must match the file. Allowed evidence is PNG/JPEG, MP4/WebM or an actual nonempty JSON/TXT runtime trace, within the gate's size bounds. A trace is a recorded runtime observation, not a hand-written assertion that checks passed.

Each `uiQuality.checks` entry names the check ID, `passed`/`failed`/`not-applicable`, a concrete observation and matching `capturePaths`. Final approved UI review covers all six IDs. System insets, responsive layout, text scaling and visual design are not optional. Keyboard/focus or motion can be `not-applicable` only with a concrete observed reason (for example, the scoped static surface has no transition), not because tools were unavailable. A failed check blocks approval; a negative review should honestly request repair, not fabricate positive captures.

Capture during the authorized implementation/runtime evidence phase, before verification freezes the source and screenshot digest. Independent reviewers read the frozen files without modifying source, captures or metadata; recapture/repair requires renewed verification. Hashes and geometry checks establish artifact integrity, not beauty, native semantics or frame rate. Source audits, goldens, browser emulation and this documentation are supplementary evidence, never a substitute for observing the actual app. If a required runtime/device or design source is unavailable, finish reachable work and report the precise unverified condition; do not disable the UI gate or claim the unseen platform passed.
