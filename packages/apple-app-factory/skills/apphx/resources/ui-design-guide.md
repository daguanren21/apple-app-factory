# apphx UI 设计指南

本指南只规定 apphx 的 UI 设计交接与验收边界，不是一套内置专家 skill。按 [宿主技能发现协议](skill-discovery.md)，从当前任务和平台出发，通过宿主的 find-skills 或等价能力搜索、评估并加载适用技能。先复用已安装且匹配的能力，不固定设计师与某个 skill 的映射，也不复制整套外部文档。

所有移动端和桌面 UI 工作同时读取 [platform-ui.md](platform-ui.md)：该文档负责各栈的安全区、键盘、窗口、文字缩放、减弱动态效果和真实画面验收；本指南负责设计权威、产品表达和设计交接。

## 1. 先确认设计权威，不另造一套系统

优先级：明确需求及实际 Figma/设计稿 → 仓库指令和已批准设计意图 → 可执行 tokens、主题、共享组件 → 同产品已验证的相邻页面 → 本指南和通用审美建议。设计稿不能取代平台可访问性和安全区要求；冲突要指出并交给其所有者处理，不能悄悄改变视觉意图或保留遮挡。

- 有 `designRef`/Figma 时读取真实节点、组件、尺寸、状态、资产和约束，记录实际可访问的来源。按其意图还原，再做平台适配；不要以“更好看”为由替换风格。
- Figma 无法访问时明确缺少的 URL/节点/权限及未验证范围。可以沿已有设计完成不依赖该来源的工作，但不能宣称已还原、伪造设计来源，或默默改成绿地设计。
- 无 Figma 时先检查现有主题、组件、图标、导航、相邻屏幕及项目已采用的设计文档。缺少 `DESIGN.md` 不代表没有设计系统；局部新增或润色继承已有视觉语言。
- 只有真正没有视觉权威的新项目才选择新方向。不要默认紫色渐变、玻璃卡片、每区块同款动画或营销页骨架；产品自己的用户任务、内容和使用场景决定构图。
- 复用既有文档约定。当前 apphx 流程已要求设计产物且没有既定等价文档时，使用 `docs/ui-design.md`；已有设计文档就更新其拥有的部分或引用它，不额外创建 `PRODUCT.md`、`DESIGN.md`、sidecar 或第二套手抄令牌表。实现与真实架构约束保持一致。

## 2. 无设计稿时，形成一个可执行的方向

先明确：谁在什么设备和环境下完成什么任务、主信息和主操作、成功与失败结果、需保留的行为、真实资产与内容、支持的窗口/设备及可访问性要求。仓库或工具能回答的事先查，不把例行决定反复交回用户。

需要额外设计方法时，按实际任务搜索并阅读候选技能的真实说明，确认其平台、工具、输入输出及权限适用性，再将所选来源和用途交给负责的 agent。搜索结果不代表已安装；不会使用的技能不得记为已使用。Impeccable 可以辅助合适的设计工作，但只是动态候选，不随 apphx 内置或强制启用。

按当前界面的用户任务选择模式：

- 操作型应用：优先清楚的信息层级、熟悉的原生交互和精确细节，不把设置/表单做成广告页。
- 阅读型页面：优先阅读顺序、行宽、缩放和定位。
- 需求确实包含营销或作品体验时，表达也必须基于真实内容，不能编造客户、指标或产品能力。

在现有设计产物或任务交接中简要写清一个连贯方向：主任务、第一屏主次关系、组件和色彩语义、内容密度、关键状态、平台适配、一个有理由的视觉/交互特征。已给定方向不重开选型；局部修改不做全产品风格探索。不要求固定数量方案、付费素材、新字体或新动画库。

## 3. 设计系统与状态交接

### 令牌与组件

引用已有可执行源及组件 API，不把文档变成另一个手动维护的 token 源。新项目才在其正式主题所有者定义最小够用的语义体系，并在设计产物记录用途：

- 颜色：背景/表面、主要与次要文本、边框、主操作、选中、危险/警告/成功，以及它们实际使用的前景/背景组合。
- 字体：标题、区块标题、正文/控件、辅助信息的语义层级，字号、行高、字重和平台文字缩放行为。使用现有/系统字体完全有效。
- 间距、圆角、层级：沿既定尺度和平台语法，同类组件一致；阴影/容器用于表达分组和层级，不为了装饰套卡片。不用通用固定网格覆盖项目已有规则。
- 动效：引用已有语义 token 或原生过渡；没有体系时只补当前场景需要的最小规则，避免每个页面散落时长/曲线。

正文及占位文本通常需至少 4.5:1 对比度；大号文本（至少 18pt 或 14pt 加粗）及关键非文本控件信息通常至少 3:1，并遵循目标平台更具体的可访问性要求。颜色不是表达状态的唯一通道。按项目支持的 light/dark/高对比模式检查，不能把暗色当简单反色，也不为未要求的模式另造系统。

### 逐屏交接

每个受影响屏幕写清进入/退出条件、主任务、导航与返回、主次操作、内容层级、滚动与固定区域、关键状态、焦点和安全区/键盘的拥有者。桌面可采用侧栏、工具栏、多栏内容与检查器，不能机械套用手机的三个竖直区块。

所有实际可达的异步或可失败状态都要覆盖：loading、empty、error/recovery、success；交互控件还需 default、focus、pressed/selected、disabled，以及支持指针时的 hover。权限不足、长文本、离线/慢请求、输入验证等按产品真实行为处理，不加入无需求的假状态。错误说明原因和恢复方式，保留用户输入；禁用项可理解，不靠颜色暗示。

可交互元素有语义名称，图标按钮有可读 label；VoiceOver/TalkBack 和桌面键盘能完成关键路径。触控目标至少符合 iOS 44×44pt / Android 48×48dp 的平台要求。长文本和大字号优先换行、重排、滚动，不靠整体缩小、截断关键文案或禁用系统缩放“适配”。

## 4. 平台适配不是网页缩放

读取 [platform-ui.md](platform-ui.md) 中实际栈的部分：Flutter、Java Android、Swift、React Native、Expo、uni-app 或 MyGo。额外技能也必须匹配真实渲染平台；不能用网页建议代替原生适配，不能为使用某个技能而换框架。

- 移动端：处理状态栏、刘海/挖孔、底部手势/主屏指示器、键盘/IME、窄屏和实际支持的方向、多窗口及大字号。一个边只有一个 inset 所有者；禁止硬编码状态栏像素、重复补偿安全区或让键盘挡住提交按钮。
- 桌面：按实际内容窗口处理标题栏、红黄绿按钮/原生 chrome、最小尺寸、宽窗、滚动、弹层、文字/显示缩放、高 DPI、指针、键盘焦点和快捷键。不是把手机页面放大；MyGo 原生 UI 与 WKWebView 都必须在真实 macOS 窗口中观察。
- 保留现有栈及原生工程；不为设计工具强行迁移、eject/prebuild、引入新包或使用另一个平台截图替代。

## 5. 动效有目的、有退路、有运行证据

按 [平台动效契约](platform-ui.md#motion-contract)，为每个实质过渡明确：触发条件、反馈/状态/空间连续性的目的、使用频率、起止状态、打断/反转方式、焦点、减弱动态效果的等价行为。需要专家方法时按任务发现相关技能，不固定动画库或技能名单。

高频操作立即响应；日常操作不等待入场表演。不盲目增加动画数量，不让成功状态只依赖动画结束回调；快速开→关→开、页面离开和取消仍应到达正确状态。优先已有或原生能力，约束滤镜/阴影/同时动画开销。系统 Reduce Motion / `prefers-reduced-motion` 要真正改变不必要的空间运动，同时保留清楚的状态反馈和焦点。

运行目标应用，观察正常、快速打断和减弱动态效果模式，并保存视频或真实 runtime trace。静态截图不能证明流畅度；没有帧时间测量就不能声称“60fps”。无合适动画是合法设计决定，不能用装饰运动充数。

## 6. 有界评审、真实证据和交付

一版连贯实现后，围绕实际画面、任务成功、可访问性、状态边界和性能观察提出具体问题。需要设计 critique、技术审计或定点 polish 时按任务选择已授权的宿主技能；不得因技能说明自行启动引擎、安装 hooks、调用付费服务或组建固定团队。性能修复只针对已观察的问题。

按用户后果排序：阻断任务/错误结果 → 状态与恢复 → 可访问性和平台适配 → 层级/组件一致性 → 动效与细节。批量修复并复看受影响场景，不为分数或泛泛“更精致”无限迭代；最多两批具体修复后仍有实质问题时交给集成所有者决策，绝不将其当成通过。最终独立评审不能由实现者自评代替。

遵循 [真实采集与验收矩阵](platform-ui.md#capture-and-acceptance-matrix)：保存实际原生画面，至少两种不同几何尺寸；包括系统区域、键盘/焦点、大字号、正常/减弱动态效果和相关状态。采集在任务配置的生成输出截图目录内、verification 冻结之前完成；最终 reviewer 只读，不补造截图或修改证据。UI gate 要求的六项检查分别给出真实观察和关联证据，失败就返回修复，不关闭 gate 来通过。

交接应清楚说明：

- 真实设计权威、所用文档/组件/token 源及未访问的来源；
- 实际修改的屏幕、状态、平台适配和动效，不夸大到未触及的应用；
- 运行的平台/设备、视口、文字与动作设置、观察结果及证据路径；
- 未解决的实质问题、未验证环境，以及哪些结论只有源代码依据。

读取过技能、代码能编译或截图文件存在，都不等于用户已经看见并能操作一个合格界面。可选技能不可用时如实说明，现有能力足够则继续；原生运行环境或必需设计来源缺失时报告准确前提，不伪造验收或设计还原结果。
